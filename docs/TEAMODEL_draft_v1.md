# 团队协作模型

## 团队角色划分
- Lead (经理)
- 产品负责人
- 需求分析员
- 架构/契约设计员
- 编码工程师（全栈）
- 代码审查员
- 安全/性能专项审查员
- 测试验证员
- 集成/发布员

## 角色职责
- Lead：澄清目标；在需求规格和契约设计基础上，拆成互不重叠的垂直功能切片；冻结契约后派工；指定共享文件唯一所有者；监控进度；最终验收
- 产品负责人：定义产品意图与优先级；审批需求契约；裁决验收争议与范围取舍；不审代码、不评技术方案
- 需求分析员：把模糊需求转成可测试的验收标准；识别边界条件、约束、假设和待确认项；产出需求契约草稿（3–8 条可观察验收标准）
- 架构/契约设计员：技术选型、模块划分、接口设计、数据模型；给出选型多维分析（成本、性能、可维护性、生态、风险、锁定效应）；建议文件所有权
- 编码工程师（全栈）：对一条垂直功能切片端到端负责：界面/交互、服务端逻辑、数据访问、单元测试
- 代码审查员：独立审查正确性、安全性、可维护性、是否符合契约和切片边界
- 安全/性能专项审查员：专项验证安全漏洞与暴露密钥、不安全编码模式；性能回归（构建大小、加载时间、关键路径延迟）；依赖供应链风险；对高风险项做 PASS / FAIL 二元门禁决策
- 测试验证员：基于验收标准做任务验证和集成验证；逐项确认需求是否被满足
- 集成/发布员：合并通过审查和验证的切片变更；做语义级依赖检查；构建部署

## 角色 Can / Cannot
- Lead：可读、可委派、可审批、指定共享文件所有者；不可写业务代码
- 产品负责人：可读需求/契约/验证证据；可批准或驳回需求契约；可裁决验收争议；可调整切片优先级；不可写代码、不可评价技术选型、不可绕过门禁
- 需求分析员：可读需求、写需求文档与需求契约草稿；不可改代码
- 架构/契约设计员：可读代码库、写设计文档与契约表；不可直接实现业务功能
- 编码工程师：只写任务书授权的切片目录；运行测试和构建命令；不可改契约/共享文件/其他切片；不可自由上网
- 代码审查员：可读代码、跑测试、写审查报告；不可改代码
- 安全/性能专项审查员：可读代码/依赖清单/构建产物；运行安全扫描、性能基准；给出 PASS / FAIL 二元门禁决策；要求补充证据；不可修复问题、不可降低安全/性能基线、不可豁免阻断项
- 测试验证员：可跑测试、读验收标准、标记通过/失败；不可改代码、不可降标准
- 集成/发布员：可合并、读各分支产物、执行 CI/CD；不可绕过门禁

## 角色输出 / 交接物

所有文档类交付物存放在 `deliverables/{slice_id}/` 下，仅使用 `.xlsx` 和 `.docx`；代码与单元测试按任务书授权目录提交，不适用此格式限制。每个 Excel 至少包含 `说明` sheet（列为 字段 / 含义 / 取值示例）加业务 sheet；业务 sheet 固定表头、判定字段用下拉。Word 以 `摘要` 开头、以 `证据指针` 结尾。

- Lead：
  - 任务切片图：Excel 格式；sheet `任务切片`：切片ID / 目标 / 可写目录 / 不可改范围 / 共享文件所有者 / 依赖切片 / 状态 / 负责人 / 预算；**可读性设计**：状态列用下拉（待派工/进行中/审查中/验证中/集成中/已完成/阻塞），人类按状态筛选即知全局进度
  - 任务书：Excel 格式；sheet `任务书`：切片ID / 目标 / 边界（可写目录、不可改范围、不可上网）/ 返回格式 / 预算 / 派工时间；**可读性设计**：每个切片一行，人类可按切片ID筛选，边界列分三段填写便于扫读
  - 进度报告：Excel 格式；sheet `进度`：时间 / 切片ID / 当前阶段 / 已完成 / 进行中 / 阻塞项 / 下一步 / 剩余预算；**可读性设计**：按时间倒序排列，最新一行即当前状态；阻塞项非空时整行标红
  - 最终验收结论：Word 格式；章节：摘要 → 四项记录核对（审查/专项/验证/集成）→ 结论（通过/不通过）→ 未决项 → 证据指针；**可读性设计**：摘要第一句必须写“通过/不通过”，四项记录核对用表格，每项一行 + 状态列
  - 总览：Excel 格式；sheet `总览`：切片ID / 目标 / 当前阶段 / 审查verdict / 专项verdict / 验证状态 / 集成状态 / 发布状态 / 最终验收结论；sheet `门禁状态`：门禁名 / 状态（未触发/进行中/通过/阻断）/ 阻塞原因 / 证据指针；sheet `待人类决策`：事项 / 类型 / 建议 / 证据指针；**可读性设计**：门禁状态用色块（未触发灰/进行中黄/通过绿/阻断红），待人类决策按紧急程度排序；**总览不参与门禁判定，仅作人类查看入口**

- 产品负责人：
  - 已批准的需求契约：Excel 格式；sheet `需求契约`：契约ID / 验收标准ID / 验收标准（可观察）/ 优先级 / 状态（已批准/驳回）/ 批准时间 / 驳回理由；**可读性设计**：状态列用下拉；驳回理由仅驳回时必填，人类按状态筛选即知哪些契约未过；**文件流转**：产品负责人批准后，将 `契约草稿` sheet 中对应行状态改为 `已批准`，并另存/重命名为 `{slice_id}_需求契约.xlsx`；驳回时保留草稿并填写驳回理由，由需求分析员修订后重新提交
  - 验收争议裁决记录：Excel 格式；sheet `裁决记录`：争议ID / 涉及契约ID / 争议点 / 裁决结果 / 理由 / 裁决时间；**可读性设计**：按时间倒序，人类可追溯每次裁决的依据

- 需求分析员：
  - 需求规格说明：Word 格式；章节：摘要 → 背景与目标 → 范围 → 边界条件 → 假设 → 待确认项（表格，每项带状态：开放/已关闭）→ 证据指针；**可读性设计**：待确认项用表格而非段落，每项带状态列，人类一眼看出哪些还开放
  - 需求契约草稿：Excel 格式；sheet `契约草稿`：契约ID / 验收标准ID / 验收标准（可观察）/ 边界条件 / 优先级 / 状态（草稿/已提交）；**可读性设计**：验收标准每行一条，不超过 8 行；状态列用下拉

- 架构/契约设计员：
  - 技术设计文档：Word 格式；章节：摘要 → 架构图 → 模块划分 → 选型多维分析（成本/性能/可维护性/生态/风险/锁定效应，每维度一列评分 + 一句话理由）→ 文件所有权建议 → 证据指针；**可读性设计**：选型分析用表格，每维度一列评分 + 一句话理由；架构图下方附一段 3 行以内的文字说明，人类不打开图也能理解
  - API 契约：Excel 格式；sheet `API契约`：接口名 / 方法 / 路径 / 请求字段 / 响应字段 / 版本 / 冻结状态（未冻结/已冻结）/ 冻结人 / 冻结时间；**可读性设计**：版本列便于识别冻结版本；请求/响应字段用 JSON 示例单元格，人类可直接复制；冻结状态用下拉，人类按“已冻结”筛选即得当前生效契约
  - 数据模型：Excel 格式；sheet `数据模型`：实体 / 字段 / 类型 / 约束 / 说明；**可读性设计**：约束列明确写出非空/唯一/默认值；每个实体第一行加粗，人类按实体分段阅读
  - 文件所有权：Excel 格式；sheet `文件所有权`：目录/文件 / 所有者角色 / 是否共享文件 / 冻结状态（未冻结/已冻结）/ 冻结人 / 冻结时间；**可读性设计**：是否共享文件列用“是/否”下拉，人类按“是”筛选即得共享文件清单；冻结状态用下拉

- 编码工程师（全栈）：
  - 可运行代码 + 单元测试：按任务书授权目录
  - 结构化报告：Excel 格式；sheet `交付报告`：结论 / 文件清单（每行一个文件 + 变更类型：新增/修改/删除）/ 测试结果（通过数/总数）/ 未覆盖原因 / 未决项 / 证据指针；**可读性设计**：文件清单每行一个文件 + 变更类型；测试结果列写成“通过数/总数”，人类不用打开测试日志即知通过率

- 代码审查员：
  - 审查报告：Excel 格式；sheet `审查报告`：审查项 / verdict（APPROVE/CHANGES_REQUESTED）/ 严重等级（阻断/高/中/低）/ 阻断项 / 建议项 / 证据指针；**可读性设计**：verdict 列用下拉；严重等级用下拉；人类按 verdict 筛选即知是否放行，按严重等级排序即知先修什么
  - 审查说明：Word 格式，可选；章节：摘要 → 审查范围 → 关键发现 → 证据指针；**可读性设计**：摘要不超过 5 行，关键发现按严重等级排序

- 安全/性能专项审查员：
  - 专项审查报告：Excel 格式；sheet `专项审查`：检查项 / 类别（安全/性能/供应链）/ verdict（PASS/FAIL）/ 严重等级 / 性能对比数据（基线→当前）/ 复现证据 / 建议修复方向 / 证据指针；**可读性设计**：verdict 和类别都用下拉；性能对比列写成“基线→当前”，人类一眼看出退化幅度；按 FAIL 筛选即得阻断项
  - 专项说明：Word 格式，可选；章节：摘要 → 检查方法 → 关键发现 → 证据指针；**可读性设计**：摘要第一句写“PASS/FAIL 及阻断项数量”

- 测试验证员：
  - 测试报告：Excel 格式；sheet `验证报告`：验收标准ID / 状态（passed/blocked）/ 缺陷ID / 证据指针；sheet `缺陷详情`：缺陷ID / 严重等级 / 复现步骤 / 期望行为 / 实际行为 / 状态；**可读性设计**：状态列用下拉；验收标准ID 必须与需求契约一一对应，人类按 blocked 筛选即知卡点；缺陷详情按严重等级排序
  - 缺陷说明：Word 格式，可选；章节：摘要 → 缺陷清单 → 复现步骤 → 证据指针；**可读性设计**：每个缺陷一节，复现步骤写成编号列表，人类可照着复现

- 集成/发布员：
  - 合并与门禁记录：Excel 格式；sheet `集成记录`：切片ID / 合并commit / 审查verdict / 专项verdict / 验证状态 / 语义检查结果 / 合并时间 / 部署状态；**可读性设计**：四个前置门禁列并排（审查/专项/验证/语义检查），人类一眼看出哪项没齐；任一未通过整行标红
  - 发布说明：Word 格式；章节：摘要 → 发布内容 → 部署状态 → 回滚方案（触发条件/步骤/验证）→ 证据指针；**可读性设计**：回滚方案写成可执行步骤（编号列表），每步含命令和预期结果，人类照着能做

## 必须硬编码的门禁

以下门禁中的文件名均相对于 `deliverables/{slice_id}/` 目录。

- 产品契约门禁：读取 `{slice_id}_需求契约.xlsx` 的 `需求契约` sheet，`状态` 列全部为 `已批准` 才放行；产品负责人驳回时，需求分析员修订后重新提交，不计入编码返工轮次
- 契约门禁：读取 `{slice_id}_API契约.xlsx` 的 `API契约` sheet 与 `{slice_id}_文件所有权.xlsx` 的 `文件所有权` sheet，`冻结状态` 列全部为 `已冻结`，且 `冻结人`、`冻结时间` 非空，才放行；契约未冻结，不得跨切片并行编码；契约变更须 Lead 审批并通知依赖方，变更后将 `冻结状态` 重置为 `未冻结`，重新冻结后方可继续并行编码
- 审查门禁：读取 `{slice_id}_审查报告.xlsx` 的 `审查报告` sheet，`verdict` 列全部为 `APPROVE` 才进入验证；任一 `CHANGES_REQUESTED` 打回编码，最大 3 轮；第 3 轮仍不通过，升级 Lead 决策
- 安全/性能专项门禁：读取 `{slice_id}_专项审查.xlsx` 的 `专项审查` sheet，`verdict` 列全部为 `PASS` 才放行；代码审查 APPROVE 且专项审查 PASS，两者都满足才进入测试验证；任一 FAIL，打回编码修复后重新提交两道审查；专项审查的阻断项不可由 Lead 或编码工程师自行豁免，必须修复后重审；确实无法修复时，升级 Lead 决策，Lead 只能选择暂停、终止、调整范围或升级产品负责人，不得放行
- 验证门禁：读取 `{slice_id}_验证报告.xlsx` 的 `验证报告` sheet，`状态` 列全部为 `passed`，且 `验收标准ID` 集合与 `{slice_id}_需求契约.xlsx` 中已批准的验收标准集合完全一致，才算通过；`blocked` 升级 Lead；验证失败打回编码，与审查共用同一轮次计数，累计 3 轮仍不通过，升级 Lead 决策
- 集成门禁：读取 `{slice_id}_集成记录.xlsx` 的 `集成记录` sheet，必须同时满足审查verdict=APPROVE、专项verdict=PASS、验证状态=passed、语义检查结果=通过，才允许合并；语义检查捕捉“Git 无冲突但逻辑已踩踏”的问题
- 发布完成门禁：集成/发布员完成构建和部署后，只能标记“部署完成”，不得直接标记“发布完成”；Lead 只有在 `{slice_id}_集成记录.xlsx` 四项前置齐全，且 `{slice_id}_最终验收.docx` 结论为“通过”后，才标记发布完成
- 最终验收：Lead 只有在“审查通过 + 专项审查 PASS + 验证通过 + 集成记录完整”四项齐全后，才给最终验收结论

## 并行与冲突规则
- 可并行：不同垂直切片、目录不重叠、契约已冻结
- 必须串行：同一目录或同一共享文件；契约未冻结；两个切片存在强语义依赖
- 冲突解决顺序：契约优先 → 文件所有权 → 语义检查兜底 → 仍无法解耦则回退串行

## 全局纪律
- 没有结构化报告，任务不标记完成。所有交接物必须包含：结论、证据指针（文件路径 / commit hash / 命令及关键输出）、未决项
- 文档类交付物仅使用 `.xlsx` 和 `.docx`；代码与测试按任务书授权目录提交，不适用此格式限制。Excel 必须包含 `说明` sheet（字段 / 含义 / 取值示例）和固定表头的业务 sheet，判定字段用下拉；Word 以 `摘要` 开头、以 `证据指针` 结尾
- 门禁只读 Excel 中约定的 sheet 和列，不读 Word 散文做判定；Word 仅做存在性检查和人类阅读
- 专项门禁的 FAIL 不可自行豁免。安全/性能专项审查的阻断项，只能通过“修复后重审”关闭；确实无法修复时升级 Lead 决策，Lead 不得直接忽略或放行
- 发布完成需要四项记录齐全：代码审查 APPROVE、专项审查 PASS、验证 passed、集成记录完整。缺一项，Lead 不得给最终验收

## 进度汇报
- 汇报对象：所有成员向 Lead 汇报；Lead 向产品负责人汇报
- 事件驱动：任务开始、门禁状态变化（APPROVE / CHANGES_REQUESTED / blocked / PASS / FAIL）、遇到阻塞、任务完成、需要 Lead 或产品负责人决策时立即汇报
- 心跳：每 10 分钟或每消耗任务预算 25% 触发一次（先到先触发）；任务预算低于 20 次工具调用时，仅按事件驱动汇报
- 内容固定：当前切片、已完成、进行中、阻塞项、下一步、剩余预算

## 共享文件清单（Lead 必须指定唯一所有者）
- 路由注册文件
- 依赖清单（package.json / requirements.txt / go.mod 等）
- 数据库迁移文件
- 全局配置文件
- CI/CD 配置
- 接口契约文件本身
- 公共工具库 / 共享组件目录
- 安全策略与依赖扫描配置
- 交付物模板（Excel 模板 / Word 模板）

## 任务书格式（Lead 派工必须四段齐全）
- 目标：本切片要交付的用户可见结果
- 边界：可写目录、可写共享文件（通常无）、不可改范围、不可上网
- 返回格式：结论 + 文件清单 + 测试结果 + 未覆盖原因 + 未决项 + 证据指针；明确交付文件名和格式（如 `{slice_id}_交付报告.xlsx`）
- 预算：最大工具调用次数，超限带现状返回
