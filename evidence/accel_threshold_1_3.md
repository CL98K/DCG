# Rust 双活倍级门槛：1.5× → 1.3× 重测证据

> 触发：用户指令「将 RUST 双活 由 1.5 提升到 1.3」，并进一步澄清为
> 「之前如果 RUST 实现的算子性能是 python 的 1.5 倍，就用 rust 的实现；现在只要比 python 快 1.3 就优先使用 rust 的」。
> 即：**倍级门槛（speedup target ratio）由 1.5× 下调到 1.3×**，让更多规模档位走 Rust。
>
> 本文件是 `evidence/accel_thresholds.py`（`:121-122` 的 `ARRAY_SIZES` 注释）所引用的重测记录。
> 环境：Windows / Python 3.13.3 / `dcg._accel` 已编译（`rt._ACC is not None`）。
> 方法：`evidence/accel_thresholds.py` 的同源两臂（`_pure(name)` = 同源代码 + `_ACC=None`）
> 交错测量、每档 5 遍取比值中位；门槛是**模块常量**的算子用「运行期改常量」做同批次 A/B，
> 门槛是**源码字面量**的算子用 exec 同源变体（已用 gate 相同的变体验证过保真度：
> 与现役函数同批次比值差 <4%，见下「方法学核验」）。

|---|---:|---|---|

## 1. `$zip`：`_ZP_MIN` 384 → 192（已实施）

方法：`rt._ZP_MIN` 在运行期设为候选值（受测臂）或 `10**9`（对照臂 = 等价纯 Python），
同批次交替，每档 3–5 遍取比值中位。受测函数是现役 `rt._zp`。

### 1.1 两列数值列（新放开的生效带逐档）

| n | 受测臂（`_ZP_MIN=192`） | 对照臂（`_ZP_MIN=1e9`） | 判定 |
|---:|---:|---:|---|
| 192 | **1.451** | 0.970 | ≥1.3 ✅ |
| 208 | **1.488** | 0.978 | ✅ |
| 224 | **1.519** | 0.981 | ✅ |
| 256 | **1.470** | 0.985 | ✅ |
| 288 | **1.539** | 0.990 | ✅ |

| 352 | **1.561** | 1.001 | ✅ |
| 383 | **1.610** | 1.015 | ✅ |

对照臂全程 0.970–1.015（≈1.0，即「同一份纯 Python 代码自比」的噪声带），
受测臂 1.451–1.610 —— 差值全部来自 Rust 路径，不是测量漂移。

### 1.2 其它数据形状（同带）

|---|---:|---:|---:|---:|

| int / str 混合 | 1.493 | — | 1.474 | — |
| 含 `None`/`bool` | 1.507 | — | 1.518 | — |

### 1.3 门槛按 `min(len(c))` 生效（不等长列验证）

输入 `(list(range(n)), list(range(n // 2)))`，门槛取两列的**较短**者：

| n | 较短列 | 是否过门槛 | 比值 |
|---:|---:|---|---:|
| 384 | 192 | 是 | 1.347 |
| 256 | 128 | 否 | ≈1.00 |

与 `runtime.py:1764-1765` 的 `min(len(c) for c in cols) >= _ZP_MIN` 语义一致。

| n | 旧门槛 384（现役） | 新门槛 192 |
|---:|---:|---:|
| 192 | 0.920 | **1.451** |

n=192 时旧门槛下比值 0.920 <1.0，即**该档今天连纯 Python 都不如**（多付一次
Rust 跨界判断），而下调门槛后是 1.451×。这是本次唯一的行为改变点。

| 列数 | n=192 | n=256 | n=320 | n=384 | n=512 | n=1024 |

| 3 列数值 | 0.999 | 0.989 | 0.996 | 1.455 | 1.441 | 1.496 |
| 3 列混合 | 1.009 | 0.999 | — | — | — | — |
| 4 列数值 | 1.040 | 0.995 | 1.002 | 1.377 | 1.381 | 1.432 |
| 5 列 | — | — | — | — | 1.273 | 1.303 |
| 6 列 | — | — | — | — | 1.257 | 1.245 |

3 列在 192–320 档全部 ≈1.0×（<1.3×），要到 384 才 1.455×；4 列 192 档只有 1.040×。
若把 `_ZP_COLS` 放宽到 3，`min(len(c)) >= 192` 会让 192–383 的三列输入白跑一次 Rust，

正确性：3 列跨门槛调用与纯 Python 逐值相同（`same: True`，768 个元素，
`[[0, 0.0, 's0'], [1, 0.5, 's1']]`）。

## 3. `$min` / `$max` / `$average` 的 `len(a) >= 24`：暂不下调

方法：exec 同源变体（把 `len(a) >= 24` 换成候选门槛），参考臂 `_pure("_mn")` 等。
每格为 5 遍比值中位。**数值列受益、非数值列回归**是这条门槛存在的全部理由，1.3× 不改变它。

### 3.4 为什么 1.3× 不构成下调理由

* 数值列在 n=12–16 就达到 2.1–2.4×，**远高于 1.3×**，门槛卡在 24 只是「晚 8–12 个元素」。
* 同一批门槛下调后，**字符串列在 n=8–32 全线 0.60–0.94×**（`$min(str)` n=8 为 0.602×、
  `$average(str)` n=8 为 0.429×）。原因：Rust 侧遇到非数值元素立即返回 `None` 让上层回退，
  但那一次跨界调用本身要几百 ns，在小列上占两成以上耗时 —— 这是**白跑**，与门槛倍数无关。
* 因此把门槛降到 16 或 12 会让「聚合用在字符串列上」的调用净变慢 15–57%，
  违反「Rust 路径任何规模不得慢于 Python」的验收条件。
* 注意：现役 24 档在字符串列上本来就是 0.68–0.94×（这是**存量**问题，非本次引入），
  本次不动它，只作为遗留问题记录（见 §6）。

## 5. `$clone` 的 `_CL_MIN_SEQ = 8`：暂不下调（冲突已定位：元素类型未控制）

候选门槛 4 的实测（`rt._CL_MIN_SEQ` 运行期改为 4，对照臂 1e9）：

| 形状 | w=4 | w=5 | w=6 | w=7 | w=8 |
|---|---:|---:|---:|---:|---:|
| list[int] | 1.263 | 0.782 | 0.848 | 0.936 | 1.020 |
| tuple[int] | 1.338 | — | — | — | 1.052 |
| list[str] | 1.317 | — | — | — | 1.049 |
| list[嵌套] | 0.97–0.99（w=4–8） | | | | |

与 `evidence/accel_thresholds.py --target 1.3` 的**无门槛臂**给出的
`$clone(list width)` 宽度 2:1.31 / 3:1.49 / 4:1.63 / 6:1.56 / 8:1.79 严重冲突
（宽度 8：1.020 vs 1.79）。已排除一种解释：`_ACC.cl` 对 w=2/3/4/5/6/7/8/16/64 的
list[int]、w=2/4/8 的 list[str] 与 tuple **都返回正确结果而非 `None`**（不触发回落）。
冲突原因**已定位**（2026-11-07 收口，见下方「结论」）：主因是**元素类型未控制** ——
两条口径的负载元素不同（标量 vs 容器），同为 w=8 时 `list<int>` 与 `list<dict>`
相差近 1.8 倍；次因才是口径差异（`_ungated` 闭包多一层帧 + `_pure` 参考臂的调用
开销差异）。**`_CL_MIN_SEQ` 仍不动**。宽度 5/6/7 实测 0.78–0.94× 已足以说明「4 不安全」。

**结论（已定位，2026-11-07）**：上表的 `list[嵌套]` 行（w=4–8 为 0.97–0.99）与
`accel_thresholds.py` 无门槛臂的 `1.63`（w=4）/`1.79`（w=8）并不矛盾 —— 它们测的是
**元素类型不同**的两个负载。`perf-candidates` 用第三种独立口径（ABBA 11 轮取中位数，
直接计时 `rt._cl`，不经 `_ungated` 闭包）重测，比值在 w 相同时：

| 负载 | 中位数 | 说明 |
|---|---:|---|
| `dict<int>` w=2 | 1.63 | 与无门槛臂的 dict 档一致 |
| `list<int>` w=4 | 0.97 | 低于门槛 → `_CL_MIN_SEQ=4` 不安全 |
| `list<int>` w=8 | 1.46 | 范围 1.30–1.58 |
| `list<dict>` w=8 | **2.55** | 范围 2.47–2.60，比 `list<int>` w=8 高近 1.8 倍 |

即：同为 `w=8`，元素是标量时 1.30–1.58×，元素本身是容器时 2.47–2.60×。
所以历史三处区间（本节表、`dcg/runtime.py` 的 `_CL_*` 注释、架构文档 §7 的 `$clone` 行）
差异的主因是**元素类型未控制**，不是测量不可信；据此 `_CL_MIN_SEQ=8` 维持不动
（标量负载 w=4 只有 0.97，容不下 4）。

## 6. 方法学核验

* **exec 变体保真度**：把 `len(a) >= 24` 替换成**同样的 24** 得到的变体，与现役
  `rt._mn` 在同一批次里对同一参考臂的比值：n=24 为 2.718 vs 2.730、n=32 为 2.988 vs 3.017、
  n=64 为 3.664 vs 3.586 —— 差 <4%，变体可信（早前 `probe_gate_13c/13d` 的 0.985 vs 2.509
  异常源于该探针把变体的 gate 设成 24 却在 n=16 上测，即「本来就该走 Python」的档位）。
* **噪声地板**：`_pure` vs `_pure` 在 n=32/96/384/1024 的比值 0.995–1.004；
  所有对照臂（门槛抬到 1e9）落在 0.97–1.02。本机空闲，噪声 ±0.5%。
* **1.3× 与噪声带的关系**：1.3 / 1.10 ≈ 1.18，即门槛高于 ±10% 噪声带上沿约 18%，
  不再有 1.5× 时代「两倍以上」的余量，因此判据必须叠加 `BORDERLINE` 边界带
  （1.3 时为 1.17–1.43，`accel_thresholds.py:326`）与多档同向（`WINDOW=3`）共同抑制误判。
  本文件所有「可下调」结论都要求**连续两档以上 ≥1.3× 且对照臂 ≈1.0**。
